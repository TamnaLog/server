# 방명록 도메인 테스트 가이드

## 테스트 대상

| API | 테스트 파일 |
| --- | --- |
| `GET /api/v1/guestbooks/write-availability` (방명록 작성 가능 여부 조회) | `app/guestbook/tests/test_get_write_availability.py` |
| `POST /api/v1/guestbooks` (방명록 작성) | `app/guestbook/tests/test_create_guestbook.py` |
| `GET /api/v1/guestbooks` (방명록 조회) | `app/guestbook/tests/test_get_guestbooks.py` |

## 작성 가능 여부 조회 테스트 의도

이 API가 판단하는 건 **"현재 사용자가 이 장소를 방문한 적이 있는가"** 하나뿐이다.
그래서 테스트의 중심은 "무엇을 보고 판단하는가"와 "무엇을 보지 않는가"를 함께 못박는 것이다.

첫째, **판단 기준이 사용자와 장소 둘 다**여야 한다. 하나라도 빠지면
다른 사람이 방문한 장소나 내가 다른 곳에 남긴 방문 기록으로 작성 가능이 되어버린다.
그래서 "다른 사용자만 방문", "다른 장소만 방문" 두 경우를 각각 `canWrite=false` 로 확인한다.

둘째, **최신 기록을 고르는 규칙**이다. 같은 장소를 여러 번 방문할 수 있으므로
`visited_at DESC, id DESC` 로 한 건만 골라야 한다. 시각이 다른 경우와 **시각이 같은 경우**를
나눠서 확인한다. (시각만으로 정렬하면 같은 시각에서 결과가 흔들린다)

셋째, **없는 장소와 방문하지 않은 장소를 구분**해야 한다. 둘 다 "쓸 수 없다"지만
전자는 `404 LOCATION_NOT_FOUND`, 후자는 `200 canWrite=false` 다. 한 테스트에서 나란히 호출해 비교한다.

넷째, **읽기 전용**이다. 조회가 방문 기록을 만들거나 바꾸면 안 되므로
정상 조회·404 조회 모두 호출 전후의 `VISITED_LOCATION` 을 비교한다.

## 주요 검증 항목

### 1. 방문 기록이 있는 경우

- 응답 전체가 명세와 일치한다. (`canWrite`, `visitedLocation.locationId` /
  `locationName` / `visitedAt` / camelCase 확인)
- `visitedAt` 은 KST 기준 **offset 없는** ISO 8601 로 내려간다.
- 여러 번 방문했으면 가장 늦은 `visited_at` 을 반환한다.
- 방문 시각이 같은 기록이 여러 개면 id 가 큰 기록을 쓴다.
- 이미 방명록을 썼는지는 보지 않으므로 두 번 조회해도 결과가 같다.

### 2. 방문 기록이 없는 경우

- `{"canWrite": false, "visitedLocation": null}` — 키를 생략하지 않는다.
- **다른 사용자만** 방문한 장소는 작성 가능이 아니다.
- **다른 장소** 방문 기록은 이 장소 판단에 영향을 주지 않는다.

### 3. 읽기 전용

- 정상 조회 후 방문 기록의 개수와 값이 그대로다.
- 방문 기록이 없을 때 새로 만들지 않는다.
- 404 로 끝난 요청도 데이터를 바꾸지 않는다.

### 4. 404 `LOCATION_NOT_FOUND`

- 장소가 없으면 404이고, **방문하지 않은 장소(200 / false)와 구분**된다.

### 5. 400 / 401

- `locationId` 누락 · 0 · 음수 · 정수 아님 → **400 `INVALID_REQUEST`**
- 토큰의 사용자가 없거나 인증 헤더가 없으면 **401 `UNAUTHORIZED_USER`**

## 작성 테스트 의도

하나의 엔드포인트가 `guestbookType` 에 따라 **다른 테이블에 저장**하고,
그 위에 파일 업로드까지 얹혀 있다. 그래서 검증 축이 네 개다.

첫째, **유형별 갈림길**이다. `GENERAL` 은 `GUESTBOOK` + 장소/방문/미션 검증,
`ROAD` 는 `ROAD_GUESTBOOK` + 좌표 저장이고 서로의 필드를 쓰지 않는다.
응답은 두 유형을 한 모델로 내려주므로 **쓰지 않는 필드가 `null` 로 들어가는지**까지 본다.
(키를 생략하면 프론트가 유형마다 다른 구조를 다뤄야 한다)

둘째, **판정 순서**다. 장소 없음(404) → 방문 이력 없음(409) → 미션 없음(404) 순서로 막고,
**미션이 있는데 미완료인 경우는 오류가 아니다.** 작성은 성공하고 `missionId` 만 `null` 이 된다.
미션 완료 판정은 유형마다 JOIN 이 달라서 문화·보물·협동 세 가지를 각각 만들어 확인한다.

셋째, **파일 처리**다. 확장자·Content-Type 을 믿지 않고 파일 내용으로 형식을 정하므로
`a.txt` 로 보낸 JPEG 이 `.jpg` 로 저장되는지 본다. 여러 개면 **요청 순서가 URL 배열 순서**여야 하고,
Blob 경로에는 방명록 id 가 들어가므로 `flush()` 로 id 를 얻은 뒤 업로드하는지도 경로로 확인한다.

넷째, **보상 삭제**다. Blob 업로드는 DB 트랜잭션에 묶이지 않으므로
중간 실패(두 번째 파일 업로드 실패)와 마지막 실패(commit 실패) 두 경우 모두
앞서 올린 파일을 전부 지우고 DB에 아무것도 남기지 않아야 한다.
Blob 호출은 `uploads` / `deletes` 픽스처로 가로채 실제 Azure 로 나가지 않는다.

### 주요 검증 항목

#### 1. 일반 방명록

- **201** 이고 응답 전체가 명세와 일치한다. (1-depth, 미사용 필드는 `null`)
- 같은 장소에 여러 번 작성하면 **매번 새 행**이 생기고 기존 행을 덮어쓰지 않는다.
- 방문 기록의 날짜와 요청 `visitedAt` 이 달라도 방문 이력만 있으면 작성된다.
- 콘텐츠 5종을 모두 생략해도 작성되고 업로드도 일어나지 않는다.

#### 2. 미션 처리

- 문화·보물·협동 각각 완료 이력이 있으면 `mission_id` 가 저장된다.
- 미션이 존재하지만 미완료면 **201 + `missionId: null`** (오류가 아니다)
- 다른 사용자만 완료한 미션은 미완료로 처리한다.

#### 3. 길바닥 방명록

- 장소·방문 이력 없이 저장되고 `location_id` 는 `null`, 좌표는 `my`=위도 / `mx`=경도로 들어간다.
- 같은 좌표에 여러 번 작성해도 매번 새 행이 생긴다.
- 업로드 경로가 `guestbook/road/{id}/...` 로 유형에 맞게 나뉜다.

#### 4. 파일 저장

- 이미지/오디오 URL 배열이 **요청 순서**와 같고 DB 컬럼에도 같은 순서로 저장된다.
- 업로드 경로는 `guestbook/{general|road}/{guestbookId}/{images|audios}` 이고
  원본 파일명은 blob 이름에 쓰지 않는다.
- 이미지 3종(JPEG/PNG/WebP)과 오디오 6종(MP3/M4A/AAC/WAV/OGG/WebM)의 확장자·Content-Type 이
  **파일 내용 기준**으로 정해진다. (파일명·Content-Type 을 다르게 보내도 실제 형식을 따른다)
- 파일이 없으면 URL 컬럼과 응답 필드가 빈 배열이 아니라 `null` 이다.

#### 5. 실패 시 되돌리기

- 두 번째 파일 업로드가 실패하면 첫 파일을 지우고 DB에 방명록이 남지 않는다.
- commit 이 실패하면 업로드한 파일을 **모두** 지운다.

#### 6. 404 / 409

- 장소 없음 → `LOCATION_NOT_FOUND`, 방문 이력 없음 → `LOCATION_NOT_VISITED`,
  미션 없음 → `MISSION_NOT_FOUND`
- 셋 다 **업로드도 저장도 일어나지 않는다.** (검증이 끝나기 전에는 Blob 을 건드리지 않는다)

#### 7. 400 / 401

- 유형별 필수 필드 누락 / 미사용 필드에 값 / 좌표 범위 초과 / 정의되지 않은 유형 /
  날짜 형식 오류 → **400 `INVALID_REQUEST`**
- 빈 파일, 허용하지 않는 형식, 이미지 10MB·오디오 30MB 초과 → **400**
- 토큰의 사용자가 없으면 **401 `UNAUTHORIZED_USER`**
- 모두 DB·Blob 에 아무것도 남기지 않는다.

## 조회 테스트 의도

내 보관함 조회라 **범위**와 **순서**가 전부다. 화면에 남의 방명록이나 지운 방명록이 섞이면 안 되고,
최신 글이 위에 와야 한다.

첫째, **조회 범위**다. 사용자와 `deleted_at IS NULL` 두 조건이 모두 걸려야 한다.
하나라도 빠지면 남의 글이 보이거나 지운 글이 되살아난다. 두 조건을 일반·길바닥 **양쪽 목록에서** 확인한다.

둘째, **정렬**이다. `saved_at DESC, id DESC` 를 DB 쿼리에서 해야 한다.
저장 시각이 다른 경우와 **같은 경우**를 나눠서 보고, 두 목록이 각각 독립적으로 정렬되는지 확인한다.

셋째, **콘텐츠 보존**이다. `NULL` 과 빈 배열(`[]`)은 다른 값이라 그대로 구분해서 내려줘야 한다.
URL 순서나 중복도 손대지 않는다. 이걸 놓치면 프론트에서 "이미지가 없다"와 "이미지를 지웠다"를 구분 못 한다.

넷째, **응답 구조**다. 유형은 항목 필드가 아니라 최상위 배열 이름으로만 구분하고,
페이지 정보나 전체 개수를 넣지 않는다. 결과가 없어도 두 배열 키는 항상 있다.

### 주요 검증 항목

#### 1. 응답 형식

- 일반 방명록은 `location`(항상 객체) 과 `mission`(없으면 `null`) 을 포함해 명세와 정확히 일치한다.
- 길바닥 방명록은 별칭·좌표를 포함하고 장소/미션 구조를 붙이지 않는다.
- 좌표는 두 유형 모두 `my`=위도 / `mx`=경도에서 온다.
- 결과가 없으면 `{"generalGuestbooks": [], "roadGuestbooks": []}`, 한 유형만 있어도 나머지는 `[]`.
- 항목에 `guestbookType` 이나 페이지 필드를 넣지 않는다. (최상위 키는 두 개뿐)

#### 2. 조회 범위

- 다른 사용자의 방명록은 두 목록 모두에서 제외된다.
- `deleted_at` 이 있는 방명록은 두 목록 모두에서 제외된다.
- 토큰을 바꾸면 결과도 그 사용자 것으로 바뀐다.

#### 3. 정렬

- 두 목록 각각 `savedAt` 내림차순이다.
- 저장 시각이 같으면 **id 가 큰 것**이 앞에 온다.
- 25건을 만들어도 전부 반환한다. (페이지네이션·상한 없음)

#### 4. 콘텐츠 보존

- URL 컬럼이 `NULL` 이면 `null`, `[]` 이면 `[]` 로 구분해서 반환한다.
- URL 배열의 순서와 중복을 그대로 유지한다.

#### 5. 읽기 전용 / 401

- 조회 후 방명록 데이터(개수·`saved_at`·`deleted_at`)가 그대로다.
- 토큰의 사용자가 없거나 인증 헤더가 없으면 **401 `UNAUTHORIZED_USER`**

## 실행 방법

```bash
# 최초 1회
pip install -r requirements-dev.txt

# 전체 테스트
pytest

# 방명록 도메인만
pytest app/guestbook

# 특정 테스트만
pytest app/guestbook/tests/test_get_write_availability.py -k 최근
pytest app/guestbook/tests/test_get_write_availability.py -k 읽기
pytest app/guestbook/tests/test_create_guestbook.py -k 미션
pytest app/guestbook/tests/test_create_guestbook.py -k 파일
pytest app/guestbook/tests/test_get_guestbooks.py -k 정렬
```

DB는 SQLite 인메모리를 사용하므로 MySQL이 떠 있지 않아도 실행된다.
공통 픽스처(`client`, `db_session`)는 루트 `conftest.py`에 있고,
장소 두 곳과 사용자 두 명은 `location_data` 픽스처에서 만든다.
방문 기록은 조합이 테스트마다 달라서 `_add_visit()` 헬퍼로 각 테스트에서 직접 만든다.
작성 테스트는 `guestbook_data` 픽스처로 장소·사용자·유형별 미션을 만들고, 미션 완료 이력은 `_complete_*_mission()` 헬퍼로 만든다.
Blob 업로드/삭제는 `uploads` / `deletes` 픽스처가 가로채므로 실제 Azure 호출은 없다.
조회 테스트는 `guestbook_data` 픽스처로 장소·미션·사용자를 만들고, 방명록은 `_add_general()` / `_add_road()` 헬퍼로 각 테스트에서 직접 만든다.

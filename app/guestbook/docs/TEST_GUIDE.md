## 작성 가능 여부 조회 테스트 의도

이 API가 판단하는 건 **"현재 사용자가 이 장소를 방문한 적이 있는가"** 하나뿐이다.
그래서 테스트의 중심은 "무엇을 보고 판단하는가"와 "무엇을 보지 않는가"를 함께 못박는 것이다.

첫째, **판단 기준이 사용자와 장소 둘 다**여야 한다. 하나라도 빠지면
다른 사람이 방문한 장소나 내가 다른 곳에 남긴 방문 기록으로 작성 가능이 되어버린다.
그래서 "다른 사용자만 방문", "다른 장소만 방문" 두 경우를 각각 `canWrite=false` 로 확인한다.

둘째, **최신 기록을 고르는 규칙**이다. 같은 장소를 여러 번 방문할 수 있으므로
`visited_at DESC, id DESC` 로 한 건만 골라야 한다. 시각이 다른 경우와 **시각이 같은 경우**를
나눠서 확인한다. (시각만으로 정렬하면 같은 시각에서 결과가 흔들린다)

셋째, **없는 장소와 방문하지 않은 장소를 구분**해야 한다. 둘 다 "쓸 수 없다"지만
전자는 `404 LOCATION_NOT_FOUND`, 후자는 `200 canWrite=false` 다. 한 테스트에서 나란히 호출해 비교한다.

넷째, **읽기 전용**이다. 조회가 방문 기록을 만들거나 바꾸면 안 되므로
정상 조회·404 조회 모두 호출 전후의 `VISITED_LOCATION` 을 비교한다.

## 주요 검증 항목

### 1. 방문 기록이 있는 경우

- 응답 전체가 명세와 일치한다. (`canWrite`, `visitedLocation.locationId` /
  `locationName` / `visitedAt` / camelCase 확인)
- `visitedAt` 은 KST 기준 **offset 없는** ISO 8601 로 내려간다.
- 여러 번 방문했으면 가장 늦은 `visited_at` 을 반환한다.
- 방문 시각이 같은 기록이 여러 개면 id 가 큰 기록을 쓴다.
- 이미 방명록을 썼는지는 보지 않으므로 두 번 조회해도 결과가 같다.

### 2. 방문 기록이 없는 경우

- `{"canWrite": false, "visitedLocation": null}` — 키를 생략하지 않는다.
- **다른 사용자만** 방문한 장소는 작성 가능이 아니다.
- **다른 장소** 방문 기록은 이 장소 판단에 영향을 주지 않는다.

### 3. 읽기 전용

- 정상 조회 후 방문 기록의 개수와 값이 그대로다.
- 방문 기록이 없을 때 새로 만들지 않는다.
- 404 로 끝난 요청도 데이터를 바꾸지 않는다.

### 4. 404 `LOCATION_NOT_FOUND`

- 장소가 없으면 404이고, **방문하지 않은 장소(200 / false)와 구분**된다.

### 5. 400 / 401

- `locationId` 누락 · 0 · 음수 · 정수 아님 → **400 `INVALID_REQUEST`**
- 토큰의 사용자가 없거나 인증 헤더가 없으면 **401 `UNAUTHORIZED_USER`**

## 작성 테스트 의도

하나의 엔드포인트가 `guestbookType` 에 따라 **다른 테이블에 저장**하고,
그 위에 파일 업로드까지 얹혀 있다. 그래서 검증 축이 네 개다.

첫째, **유형별 갈림길**이다. `GENERAL` 은 `GUESTBOOK` + 장소/방문/미션 검증,
`ROAD` 는 `ROAD_GUESTBOOK` + 좌표 저장이고 서로의 필드를 쓰지 않는다.
응답은 두 유형을 한 모델로 내려주므로 **쓰지 않는 필드가 `null` 로 들어가는지**까지 본다.
(키를 생략하면 프론트가 유형마다 다른 구조를 다뤄야 한다)

둘째, **판정 순서**다. 장소 없음(404) → 방문 이력 없음(409) → 미션 없음(404) 순서로 막고,
**미션이 있는데 미완료인 경우는 오류가 아니다.** 작성은 성공하고 `missionId` 만 `null` 이 된다.
미션 완료 판정은 유형마다 JOIN 이 달라서 문화·보물·협동 세 가지를 각각 만들어 확인한다.

셋째, **파일 처리**다. 확장자·Content-Type 을 믿지 않고 파일 내용으로 형식을 정하므로
`a.txt` 로 보낸 JPEG 이 `.jpg` 로 저장되는지 본다. 여러 개면 **요청 순서가 URL 배열 순서**여야 하고,
Blob 경로에는 방명록 id 가 들어가므로 `flush()` 로 id 를 얻은 뒤 업로드하는지도 경로로 확인한다.

넷째, **보상 삭제**다. Blob 업로드는 DB 트랜잭션에 묶이지 않으므로
중간 실패(두 번째 파일 업로드 실패)와 마지막 실패(commit 실패) 두 경우 모두
앞서 올린 파일을 전부 지우고 DB에 아무것도 남기지 않아야 한다.
Blob 호출은 `uploads` / `deletes` 픽스처로 가로채 실제 Azure 로 나가지 않는다.

다섯째, **오디오 제목 생성**이다. 제목은 프론트가 보내는 값이 아니라 서버가 OpenAI 로 만든다.
그래서 "오디오가 없으면 **호출 자체가 없어야** 한다"가 응답만 봐서는 확인되지 않는다.
(둘 다 `audioTitle: null` 이라 결과가 같다) 그래서 스텁이 **호출 인자를 기록**하게 해서
호출 횟수를 직접 본다. 오디오가 여러 개여도 제목은 하나이므로 호출은 한 번뿐이다.
생성 실패는 부가 기능 실패가 아니라 **작성 전체 실패**라, 500 과 함께
DB 행도 업로드한 파일도 남지 않는지 함께 확인한다.
모듈 자체 규칙(전사 순서·길이 규칙·실패 처리)은 HTTP 만 가짜로 바꿔
`test_audio_title.py` 에서 따로 본다.

여섯째, **기온**이다. `DECIMAL(4,1)` 컬럼이라 범위와 정밀도를 스키마에서 막는다.
`24.55` 처럼 소수 둘째 자리가 오면 **반올림하지 않고 400** 이어야 해서,
"저장은 되는데 값이 조용히 바뀌는" 경우를 막으려고 경계값과 함께 확인한다.

### 주요 검증 항목

#### 1. 일반 방명록

- **201** 이고 응답 전체가 명세와 일치한다. (1-depth, 미사용 필드는 `null`)
- 같은 장소에 여러 번 작성하면 **매번 새 행**이 생기고 기존 행을 덮어쓰지 않는다.
- 방문 기록의 날짜와 요청 `visitedAt` 이 달라도 방문 이력만 있으면 작성된다.
- 콘텐츠 5종을 모두 생략해도 작성되고 업로드도 일어나지 않는다.

#### 2. 미션 처리

- 문화·보물·협동 각각 완료 이력이 있으면 `mission_id` 가 저장된다.
- 미션이 존재하지만 미완료면 **201 + `missionId: null`** (오류가 아니다)
- 다른 사용자만 완료한 미션은 미완료로 처리한다.

#### 3. 길바닥 방명록

- 장소·방문 이력 없이 저장되고 `location_id` 는 `null`, 좌표는 `my`=위도 / `mx`=경도로 들어간다.
- 같은 좌표에 여러 번 작성해도 매번 새 행이 생긴다.
- 업로드 경로가 `guestbook/road/{id}/...` 로 유형에 맞게 나뉜다.

#### 4. 파일 저장

- 이미지/오디오 URL 배열이 **요청 순서**와 같고 DB 컬럼에도 같은 순서로 저장된다.
- 업로드 경로는 `guestbook/{general|road}/{guestbookId}/{images|audios}` 이고
  원본 파일명은 blob 이름에 쓰지 않는다.
- 이미지 3종(JPEG/PNG/WebP)과 오디오 6종(MP3/M4A/AAC/WAV/OGG/WebM)의 확장자·Content-Type 이
  **파일 내용 기준**으로 정해진다. (파일명·Content-Type 을 다르게 보내도 실제 형식을 따른다)
- 파일이 없으면 URL 컬럼과 응답 필드가 빈 배열이 아니라 `null` 이다.

#### 5. 오디오 제목 생성 (`audioTitle`)

- 오디오가 없으면 **OpenAI 를 호출하지 않고** `audioTitle` 은 `null` 이다.
- 오디오가 있으면 생성된 제목을 DB와 응답에 **같은 값으로** 넣는다. (일반·길바닥 모두)
- 오디오가 여러 개여도 **호출은 한 번**이고 제목도 하나다. 전달되는 오디오는 요청 순서를 지킨다.
- 업로드와 제목 생성은 **같은 바이트**를 쓴다. (업로드 스트림을 두 번 읽지 않는다)
- 생성 실패는 **500** 이고 DB 행도, 이미 올린 이미지·오디오도 남지 않는다.

모듈 단위(`test_audio_title.py`)에서는 HTTP 만 가짜로 바꿔 다음을 본다.

- 여러 오디오를 요청 순서대로 전사해 이어 붙이고 제목 생성은 한 번만 호출한다.
- 전사 요청은 설정된 모델과 **판별된 실제 형식**(확장자·Content-Type)으로 보낸다.
- 제목 요청은 모듈 상수 프롬프트 + 짧은 출력 토큰 + 낮은 무작위성을 쓴다.
- 출력의 앞뒤 공백·따옴표·둘째 줄을 정리해 **한 줄 제목**으로 만든다.
- 10자를 넘으면 더 짧게 **한 번만** 다시 만들고, 그래도 길면 **자르지 않는다.**
  50자를 넘으면 실패로 처리한다.
- API 키 없음 / 시간 초과 / HTTP 오류 / 빈 전사문 / 빈 제목은 모두 예외다. (→ 500)

#### 6. 기온 (`contentTemperatureCelsius`)

- 소수 첫째 자리·정수·영하·경계값(`±999.9`)을 저장하고 **JSON 숫자**로 반환한다.
- 보내지 않으면 `null` 로 저장한다. (일반·길바닥 모두 사용 가능)
- 범위 초과, **소수 둘째 자리**, 숫자가 아닌 값은 반올림하지 않고 **400** 이며 행이 남지 않는다.

#### 7. 실패 시 되돌리기

- 두 번째 파일 업로드가 실패하면 첫 파일을 지우고 DB에 방명록이 남지 않는다.
- commit 이 실패하면 업로드한 파일을 **모두** 지운다.

#### 8. 404 / 409

- 장소 없음 → `LOCATION_NOT_FOUND`, 방문 이력 없음 → `LOCATION_NOT_VISITED`,
  미션 없음 → `MISSION_NOT_FOUND`
- 셋 다 **업로드도 저장도 일어나지 않는다.** (검증이 끝나기 전에는 Blob 을 건드리지 않는다)

#### 9. 400 / 401

- 유형별 필수 필드 누락 / 미사용 필드에 값 / 좌표 범위 초과 / 정의되지 않은 유형 /
  날짜 형식 오류 → **400 `INVALID_REQUEST`**
- 빈 파일, 허용하지 않는 형식, 이미지 10MB·오디오 30MB 초과 → **400**
- 토큰의 사용자가 없으면 **401 `UNAUTHORIZED_USER`**
- 모두 DB·Blob 에 아무것도 남기지 않는다.

## 조회 테스트 의도

전체 방명록 조회라 **범위**와 **순서**가 전부다. 작성자와 관계없이 모든 활성 방명록이 포함되고,
지운 방명록은 제외되며 최신 글이 위에 와야 한다.

첫째, **조회 범위**다. 작성자 조건 없이 `deleted_at IS NULL`만 적용해야 한다.
현재 사용자와 다른 사용자의 글이 모두 나오고 삭제된 글만 제외되는지 일반·길바닥 **양쪽 목록에서** 확인한다.

둘째, **정렬**이다. `saved_at DESC, id DESC` 를 DB 쿼리에서 해야 한다.
저장 시각이 다른 경우와 **같은 경우**를 나눠서 보고, 두 목록이 각각 독립적으로 정렬되는지 확인한다.

셋째, **콘텐츠 보존**이다. `NULL` 과 빈 배열(`[]`)은 다른 값이라 그대로 구분해서 내려줘야 한다.
URL 순서나 중복도 손대지 않는다. 이걸 놓치면 프론트에서 "이미지가 없다"와 "이미지를 지웠다"를 구분 못 한다.

넷째, **응답 구조**다. 유형은 항목 필드가 아니라 최상위 배열 이름으로만 구분하고,
페이지 정보나 전체 개수를 넣지 않는다. 결과가 없어도 세 배열 키는 항상 있다.

다섯째, **좋아요**다. `isLiked` 는 현재 사용자 기준, `likeCount` 는 사용자 구분 없는 전체 개수라
기준이 서로 다르다. 테스트 데이터에 사용자가 한 명뿐이면 두 값이 같이 움직여서
조건을 잘못 걸어도 통과한다. 그래서 "다른 사람만 누른 좋아요"(→ `false` / `1`)를 따로 만든다.
취소는 행 삭제가 아니라 `deleted_at` 이므로 **취소된 좋아요가 개수에 남지 않는지**도 확인한다.
유형마다 좋아요 테이블이 다르고 두 방명록 테이블은 id 가 겹칠 수 있어서,
유형별 id 를 다르게 두면 테이블을 잘못 골라도 드러나지 않는다.
그래서 **같은 id 를 두 테이블에 모두 만들어** 좋아요가 서로 섞이지 않는지 확인한다.

여섯째, **방문 장소**다. `visitedLocations` 는 `VISITED_LOCATION` 만 보고 만들며,
같은 장소를 여러 번 방문해도 한 번만 담는다. 방문 기록을 그대로 나열하면 중복이 생기고,
장소별로 묶지 않으면 정렬 기준(장소별 **가장 최근** 방문)이 틀어진다.
방명록에서 장소를 유추하는 구현을 막으려고 "방명록만 있고 방문 기록은 없는" 경우도 확인한다.

### 주요 검증 항목

#### 1. 응답 형식

- 일반 방명록은 `location`(항상 객체) 과 `mission`(없으면 `null`) 을 포함해 명세와 정확히 일치한다.
- 길바닥 방명록은 별칭·좌표를 포함하고 장소/미션 구조를 붙이지 않는다.
- 좌표는 두 유형 모두 `my`=위도 / `mx`=경도에서 온다.
- 결과가 없으면 세 배열 모두 `[]`, 한 유형만 있어도 나머지는 `[]`.
- 항목에 `guestbookType` 이나 페이지 필드를 넣지 않는다.
  (최상위 키는 `visitedLocations` / `generalGuestbooks` / `roadGuestbooks` 세 개뿐)
- 두 유형 모두 작성자 정보(`userId` / `userNickname` / `characterImgUrl`)를 함께 준다.
  배정된 AR 캐릭터가 없으면 `characterImgUrl` 은 `null`, 닉네임이 없으면 `userNickname` 도 `null`.
- `audioTitle` 과 `contentTemperatureCelsius` 는 값이 없어도 키를 생략하지 않고 `null` 이며,
  기온은 문자열이 아니라 **JSON 숫자**다. (영하 값 포함)

#### 1-1. 좋아요 (일반·길바닥 방명록)

- 좋아요가 없으면 `isLiked: false` / `likeCount: 0`.
- 현재 사용자가 눌렀으면 `isLiked: true`, **다른 사용자만** 눌렀으면 `false` 지만 개수에는 포함된다.
- 취소된(소프트 삭제) 좋아요는 `isLiked` 와 `likeCount` 양쪽에서 빠진다.
- 다른 방명록의 좋아요가 섞이지 않는다.
- 일반 방명록은 `GUESTBOOK_LIKE`, 길바닥 방명록은 `ROAD_GUESTBOOK_LIKE`만 반영하며 두 유형의 좋아요가 섞이지 않는다.
- 두 유형 모두 응답에 `isLiked` / `likeCount` 키를 항상 포함한다.
- 한 사용자는 각 유형의 같은 방명록에 좋아요 행을 하나만 가진다. (각 테이블의 유니크 제약 확인)

#### 1-2. 방문 장소 (`visitedLocations`)

- 방문한 장소를 `id` 와 `locationTitle` 만으로 반환한다.
- 같은 장소를 여러 번 방문해도 **한 번만** 담는다.
- 장소별 **가장 최근 방문 시각** 내림차순이고, 같으면 장소 id 가 큰 순이다.
- 다른 사용자의 방문 기록은 제외한다.
- 방명록이 없어도 방문 장소는 그대로 내려주고, 반대로 방명록만 있고 방문 기록이 없으면 `[]` 다.

#### 2. 조회 범위

- 다른 사용자의 방명록도 두 목록에 포함되고, 작성자 정보는 방명록마다 각자의 것이 붙는다.
- `deleted_at` 이 있는 방명록은 두 목록 모두에서 제외된다.
- 토큰을 바꿔도 **목록 자체는 같다.** 토큰에 따라 달라지는 값은
  `isLiked` 와 `visitedLocations` 뿐이고 `likeCount` 는 그대로다.

#### 3. 정렬

- 두 목록 각각 `savedAt` 내림차순이다.
- 저장 시각이 같으면 **id 가 큰 것**이 앞에 온다.
- 25건을 만들어도 전부 반환한다. (페이지네이션·상한 없음)

#### 4. 콘텐츠 보존

- URL 컬럼이 `NULL` 이면 `null`, `[]` 이면 `[]` 로 구분해서 반환한다.
- URL 배열의 순서와 중복을 그대로 유지한다.

#### 5. 읽기 전용 / 401

- 조회 후 방명록 데이터(개수·`saved_at`·`deleted_at`)가 그대로다.
- 토큰의 사용자가 없거나 인증 헤더가 없으면 **401 `UNAUTHORIZED_USER`**

## 좋아요 테스트 의도

좋아요는 **토글이 아니라 최종 상태를 지정하는 API** 다. `isLiked` 를 "현재 상태를 뒤집어라"로
구현해도 **한 번만 호출하는 테스트에서는 결과가 같아서** 통과해 버린다.
그래서 같은 요청을 세 번 보내 결과가 계속 같은지(멱등) 확인한다.

두 번째로 조심할 곳은 **취소의 의미**다. 취소는 행 삭제가 아니라 `deleted_at` 기록이라,
`DELETE` 로 구현해도 "취소 후 개수 0" 은 똑같이 통과한다.
그래서 개수뿐 아니라 **행이 그대로 남아 있는지**와, 다시 눌렀을 때
새 행이 아니라 **같은 행이 되살아나는지**(`created_at` 유지)를 함께 본다.

세 번째는 **유형별 테이블 분리**다. 두 방명록 테이블은 id 가 겹칠 수 있어서
`guestbookId` 만으로 대상을 정하면 엉뚱한 방명록에 좋아요가 달린다.
테스트 데이터에 유형별 id 를 다르게 두면 이 실수가 드러나지 않으므로,
**같은 id 를 두 테이블에 모두 만들어** 요청 유형의 테이블만 쓰는지 확인한다.
선택한 유형에서 못 찾았을 때 다른 테이블을 뒤지지 않는지도(404) 함께 본다.

네 번째는 **판정 순서**다. 삭제된 방명록은 작성자와 관계없이 없는 것으로 봐야 하므로,
"삭제된 **내** 방명록" 은 409 가 아니라 404 여야 한다. 순서를 바꾸면 이 케이스만 틀린다.

마지막으로 **flush 시점**이다. 세션이 `autoflush=False` 라서 상태를 바꾼 뒤 flush 하지 않으면
바로 뒤에 세는 `likeCount` 에 방금 바꾼 값이 반영되지 않는다.
응답의 `isLiked` 는 요청 값 그대로라 맞게 나오므로 **`likeCount` 로만 잡히는 실수**다.

### 주요 검증 항목

#### 1. 좋아요 설정 (`isLiked: true`)

- 처음 누르면 **200** + `isLiked: true` + `likeCount: 1` 이고 활성 행이 하나 생긴다.
- 취소했던 좋아요는 **새 행을 만들지 않고** `deleted_at` 만 지운다. (`created_at` 유지)
- 이미 좋아요 상태면 행의 id·`created_at` 을 그대로 두고 성공만 반환한다.
- 같은 요청을 여러 번 보내도 응답과 행 수가 같다. (멱등)

#### 2. 좋아요 취소 (`isLiked: false`)

- 활성 좋아요는 **하드 삭제하지 않고** `deleted_at` 을 기록한다. (행은 남는다)
- 누른 적이 없으면 행을 만들지 않고 `likeCount: 0` 을 반환한다.
- 이미 취소된 상태면 `deleted_at` 값을 **다시 쓰지 않는다.**
- 눌렀다 취소했다 다시 눌러도 행은 하나다.

#### 3. `likeCount`

- 사용자 구분 없이 활성 좋아요를 모두 센다. (방금 누른 내 좋아요 포함)
- 취소된 좋아요와 **다른 방명록**의 좋아요는 세지 않는다.
- 일반/길바닥 좋아요 수가 서로 섞이지 않는다.

#### 4. 유형별 테이블

- `GENERAL` 은 `GUESTBOOK` + `GUESTBOOK_LIKE`, `ROAD` 는 `ROAD_GUESTBOOK` + `ROAD_GUESTBOOK_LIKE`.
- 같은 id 가 두 테이블에 있어도 **요청 유형의 테이블에만** 좋아요가 생긴다.
- 유형과 실제 저장 테이블이 다르면 **404** 이고 다른 유형을 추가로 조회하지 않는다.

#### 5. 동시 요청

- 조회 직후 다른 요청이 행을 먼저 만든 상황에서도 **중복 행을 만들지 않고**
  기존 행을 되살린다. (유니크 제약 충돌 → 재조회 후 상태 적용)

#### 6. 404 / 409

- 없는 방명록 / 소프트 삭제된 방명록 → **404 `GUESTBOOK_NOT_FOUND`** (일반·길바닥 모두)
- 본인 방명록 → **409 `OWN_GUESTBOOK_LIKE_NOT_ALLOWED`** (`isLiked` 값과 무관, 일반·길바닥 모두)
- **삭제된 본인 방명록은 409 가 아니라 404** 다. (존재 검사가 먼저)
- 셋 다 좋아요 행이 생기지 않는다.

#### 7. 400 / 401

- `guestbookType` / `isLiked` 누락, 정의되지 않은 유형(소문자 포함),
  불리언이 아닌 `isLiked`, 정의되지 않은 필드, 빈 body → **400 `INVALID_REQUEST`**
- `guestbookId` 가 0·음수·정수가 아니면 **400**
- 인증 헤더가 없거나 토큰의 사용자가 없으면 **401 `UNAUTHORIZED_USER`**
- 모두 좋아요 행이 남지 않는다.

## 실행 방법

```bash
# 최초 1회
pip install -r requirements-dev.txt

# 전체 테스트
pytest

# 방명록 도메인만
pytest app/guestbook

# 특정 테스트만
pytest app/guestbook/tests/test_get_write_availability.py -k 최근
pytest app/guestbook/tests/test_get_write_availability.py -k 읽기
pytest app/guestbook/tests/test_create_guestbook.py -k 미션
pytest app/guestbook/tests/test_create_guestbook.py -k 파일
pytest app/guestbook/tests/test_get_guestbooks.py -k 정렬
pytest app/guestbook/tests/test_set_guestbook_like.py -k 취소
pytest app/guestbook/tests/test_audio_title.py
```

DB는 SQLite 인메모리를 사용하므로 MySQL이 떠 있지 않아도 실행된다.
공통 픽스처(`client`, `db_session`)는 루트 `conftest.py`에 있고,
장소 두 곳과 사용자 두 명은 `location_data` 픽스처에서 만든다.
방문 기록은 조합이 테스트마다 달라서 `_add_visit()` 헬퍼로 각 테스트에서 직접 만든다.
작성 테스트는 `guestbook_data` 픽스처로 장소·사용자·유형별 미션을 만들고, 미션 완료 이력은 `_complete_*_mission()` 헬퍼로 만든다.
Blob 업로드/삭제는 `uploads` / `deletes` 픽스처가 가로채므로 실제 Azure 호출은 없다.
OpenAI 호출도 나가지 않는다. 작성 테스트는 `audio_titles` 픽스처가 제목 생성을 가로채고,
`test_audio_title.py` 는 `httpx.Client` 자체를 가짜로 바꾼다.
좋아요 테스트는 `like_data` 픽스처로 사용자 3명과 유형별 방명록(남의 것 / 내 것 / 삭제된 것)을 만든다.
본인 방명록에는 좋아요를 누를 수 없으므로 좋아요 대상은 항상 다른 사용자의 방명록이다.
조회 테스트는 `guestbook_data` 픽스처로 장소·미션·사용자를 만들고, 방명록은 `_add_general()` / `_add_road()` 헬퍼로 각 테스트에서 직접 만든다.

# 익명 사용자 발급 비즈니스 룰

## 1. 호출 기준

- HTTP 메서드: `POST`
- 엔드포인트: `/api/v1/auth/anonymous`
- 요청 Query, Path, Body는 사용하지 않는다.
- `Authorization` 헤더를 요구하지 않는다.

프론트는 앱 실행 시 기기 보안 저장소에서 기존 액세스 토큰을 먼저 확인한다.

- 저장된 토큰이 있으면 이 API를 호출하지 않고 기존 토큰을 사용한다.
- 저장된 토큰이 없으면 이 API를 호출하여 새로운 익명 사용자와 토큰을 발급받는다.

백엔드는 앱의 최초 실행 여부를 직접 판단하거나 감시하지 않는다. 토큰 보유 여부 확인과 API 호출 여부 판단은 프론트의 책임이다.

## 2. 처리 순서

1. 암호학적으로 안전한 랜덤 액세스 토큰 원문을 생성한다.
2. 토큰 원문을 SHA-256으로 해시한다.
3. 익명 사용자용 닉네임 5개 중 하나를 무작위로 선택한다.
4. 토큰 해시와 닉네임을 포함한 새로운 `USER`를 생성한다.
5. 생성된 사용자의 기본 `USER_SETTING`을 생성한다.
6. 사용자와 사용자 설정을 하나의 트랜잭션으로 커밋한다.
7. 커밋에 성공하면 토큰 원문과 토큰 타입을 프론트에 반환한다.

정상적으로 새로운 익명 사용자를 생성하면 `201 Created`를 반환한다.

## 3. 액세스 토큰 생성

액세스 토큰 원문은 Python 표준 라이브러리의 `secrets.token_urlsafe(32)`로 생성한다.

```python
import secrets

access_token = secrets.token_urlsafe(32)
```

이 방식은 32바이트의 암호학적 난수를 URL-safe Base64 문자열로 변환한다. 일반적인 결과는 약 43자이며 예측이나 무작위 대입이 사실상 불가능한 충분한 엔트로피를 가진다.

토큰 원문에는 사용자 id나 개인정보를 포함하지 않는다.

## 4. 토큰 해시 생성 및 저장

토큰 원문은 SHA-256의 16진수 문자열로 변환한다.

```python
import hashlib

access_token_hash = hashlib.sha256(
    access_token.encode("utf-8")
).hexdigest()
```

`hexdigest()`의 결과는 항상 64자이므로 ERD의 `USER.access_token_hash CHAR(64)`에 저장한다.

- 프론트에 반환하는 값: 액세스 토큰 원문
- DB에 저장하는 값: `access_token_hash`
- DB에 저장하지 않는 값: 액세스 토큰 원문

해시는 복호화하지 않는다. 이후 요청에서 받은 토큰 원문을 같은 방식으로 해시한 뒤 DB의 `access_token_hash`와 비교한다.

`USER.access_token_hash`의 `UNIQUE` 제약으로 하나의 토큰 해시가 두 사용자에게 연결되지 않도록 한다.

## 5. 사용자 생성값

새로운 익명 사용자는 다음 값으로 `USER`에 저장한다.

| 컬럼 | 저장값 |
| --- | --- |
| `id` | DB 자동 증가 값 |
| `expectation` | `NULL` |
| `transportation` | `NULL` |
| `travel_style` | `NULL` |
| `user_travel_style_id` | `NULL` |
| `ar_character_id` | `NULL` |
| `nickname` | 익명 사용자용 닉네임 5개 중 무작위로 선택한 값 |
| `point` | `0` |
| `access_token_hash` | 생성한 액세스 토큰의 SHA-256 해시 |

`created_at`과 `updated_at`은 DB 기본값인 현재 시각을 사용한다.

익명 사용자 발급 단계에서는 온보딩 정보, 여행 유형과 AR 캐릭터를 정하지 않는다. 해당 정보는 이후 온보딩 API에서 기존 `USER` 행을 수정하여 저장한다.

닉네임 후보는 서비스 코드에 다음 상수로 정의한다.

```python
ANONYMOUS_NICKNAMES = (
    "몽글몽글파도",
    "한라봉주스",
    "오름러버",
    "돌담산책",
    "귤빛노을",
)
```

Python의 `secrets.choice(ANONYMOUS_NICKNAMES)`로 하나를 선택하여 `USER.nickname`에 저장한다.

`USER.nickname`에는 `UNIQUE` 제약이 없으므로 서로 다른 사용자에게 같은 닉네임이 배정될 수 있다. 닉네임 중복은 오류로 처리하거나 다시 추첨하지 않는다.

## 6. 사용자 설정 생성

`USER`를 생성하고 id를 확보한 후 다음 값으로 `USER_SETTING`을 생성한다.

| 컬럼 | 저장값 |
| --- | --- |
| `user_id` | 새로 생성한 `USER.id` |
| `push_notification` | `TRUE` |
| `near_mission_notification` | `TRUE` |

`created_at`과 `updated_at`은 DB 기본값인 현재 시각을 사용한다.

익명 사용자가 생성되면 사용자 설정도 정확히 한 행 존재해야 한다. ERD는 `USER`와 `USER_SETTING`을 선택적 1:1 관계로 허용하지만, 익명 사용자 발급 API의 서비스 로직에서는 두 데이터를 항상 함께 생성한다.

## 7. 응답 데이터

응답에는 다음 값만 포함한다.

```json
{
  "accessToken": "발급한 토큰 원문",
  "tokenType": "Bearer"
}
```

사용자 id와 `access_token_hash`는 응답하지 않는다.

토큰 원문은 이 응답에서만 확인할 수 있다. 백엔드는 해시만 저장하므로 응답 이후 동일한 토큰 원문을 DB에서 복구하여 다시 전달할 수 없다.

프론트는 응답을 받은 즉시 다음 보안 저장소에 토큰 원문을 저장한다.

- iOS: Keychain
- Android: Keystore 기반 보안 저장소

기기 저장소에 토큰을 기록하는 것은 프론트의 책임이며 백엔드가 직접 수행할 수 없다.

## 8. 이후 요청의 사용자 식별

익명 사용자 발급 API를 제외한 인증 필요 API에서 프론트는 다음 헤더를 전송한다.

```http
Authorization: Bearer {accessToken}
```

공통 `get_current_user_id()`는 다음 순서로 현재 사용자를 식별한다.

1. `Authorization` 헤더가 존재하고 인증 방식이 `Bearer`인지 확인한다.
2. Bearer 토큰 원문을 추출한다.
3. 토큰 원문을 익명 사용자 발급 시점과 동일한 SHA-256 방식으로 해시한다.
4. `USER.access_token_hash`가 계산된 해시와 일치하는 사용자를 조회한다.
5. 사용자가 존재하면 해당 `USER.id`를 현재 사용자 id로 반환한다.

토큰이 누락됐거나 일치하는 사용자가 없으면 `401 UNAUTHORIZED_USER`를 반환한다.

```json
{
  "code": "UNAUTHORIZED_USER"
}
```

토큰 원문이나 해시는 로그, 오류 응답 또는 예외 메시지에 포함하지 않는다.

## 9. 토큰 충돌 처리

토큰 해시 저장 시 `USER.access_token_hash`의 `UNIQUE` 제약 위반이 발생하면 사용자 생성 트랜잭션을 롤백한다.

새로운 액세스 토큰을 생성하여 사용자 생성 전체 과정을 다시 시도한다. 정해진 재시도 횟수 안에 저장하지 못하면 공통 `500 INTERNAL_SERVER_ERROR`로 처리한다.

충돌로 실패한 토큰 원문은 프론트에 반환하지 않는다.

## 10. 중복 호출과 앱 재설치

이 API는 호출할 때마다 새로운 `USER`와 새로운 액세스 토큰을 생성한다. 같은 기기에서 같은 요청을 반복해도 기존 사용자를 찾아 재사용하지 않는다.

프론트는 기기 보안 저장소에 기존 토큰이 있을 때 이 API를 다시 호출하지 않아야 한다.

앱을 삭제하거나 기기 저장소가 초기화되어 기존 토큰을 잃으면 기존 익명 사용자를 복구할 수 없으며, 다시 호출할 때 새로운 사용자가 생성된다.

현재 ERD에는 토큰 만료, 재발급, 폐기와 다른 기기로의 사용자 복구를 위한 컬럼이나 세션 테이블이 없다. 따라서 해당 기능은 이 API의 범위에 포함하지 않는다.

## 11. 트랜잭션

`USER` 생성, 토큰 해시 저장과 `USER_SETTING` 생성은 하나의 트랜잭션으로 처리한다.

사용자 또는 사용자 설정 중 하나라도 저장에 실패하면 전체 작업을 롤백하고 토큰 원문을 응답하지 않는다. 따라서 설정이 없는 사용자나 사용자 없이 남은 설정 데이터가 생성되지 않아야 한다.

커밋이 완료된 후에만 `201 Created` 응답을 반환한다.

## 12. 오류 처리

### 500 `INTERNAL_SERVER_ERROR`

다음 경우 트랜잭션을 롤백하고 공통 `500` 오류를 반환한다.

- 액세스 토큰 생성 또는 해시 처리에 실패한 경우
- 사용자 저장에 실패한 경우
- 사용자 설정 저장에 실패한 경우
- 토큰 충돌 재시도 횟수를 초과한 경우
- 그 밖의 예상하지 못한 DB 또는 서버 오류

```json
{
  "code": "INTERNAL_SERVER_ERROR"
}
```

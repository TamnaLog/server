# 기타 도메인 테스트 가이드

## 테스트 대상

| API | 테스트 파일 |
| --- | --- |
| `PUT /api/v1/users/me/step-counts` (걸음 수 저장) | `app/others/tests/test_save_step_count.py` |
| `POST /api/v1/users/me/gps` (GPS 및 방문 장소 저장) | `app/others/tests/test_save_gps.py` |
| 방문 장소 판정 (GPS 저장 보조) | `app/others/tests/test_visit_detector.py` |

## 걸음 수 저장 테스트 의도

저장 API 하나지만 **"같은 시각이면 덮어쓴다"** 와 **"목표를 달성하면 캐릭터를 준다"**
두 규칙이 한 트랜잭션에 들어 있어서 조심할 곳이 다섯 군데다.

첫째, **`saved_at` 의 의미**다. 컬럼 이름은 "저장 시각"처럼 보이지만 실제로는
**프론트가 걸음 수를 측정한 시각**(`recordedAt`)이다. 서버 수신 시각으로 바꾸거나
KST 자정으로 정규화하면 안 되므로 **DB 행을 직접 열어** 요청값 그대로인지 본다.

둘째, **덮어쓰기 방향**이다. 프론트가 보낸 값이 그 시점의 최종값이라
**기존 값보다 작아도 그대로 교체**해야 한다. "누적이니까 큰 값이 맞겠지"라고
`max()`를 쓰거나 더해 버리기 쉬운데, 값을 늘리는 방향으로만 테스트하면 그 실수가 드러나지 않는다.
그래서 9000 → 120처럼 **줄어드는 요청**을 따로 만든다.

셋째, **행이 늘지 않는 것**이다. 같은 시각으로 다시 보내면 `UPDATE` 여야 하는데
`INSERT` 로 구현해도 "마지막 값이 남는지"만 보면 통과한다. (최신 행을 읽으면 값은 맞다)
그래서 값뿐 아니라 **행 개수와 `created_at` 유지**를 함께 본다.
하나의 행은 `(사용자, 측정 시각)` 조합에 묶이므로 "시각만 다른 요청"과
"사용자만 다른 기록"을 각각 만들어 키의 범위도 확인한다.

넷째, **추첨과 획득의 분리**다. 추첨 결과는 무작위라 값 자체를 단정할 수 없으므로
**DB 의 후보 캐릭터(1~3) 중 하나인지**로 확인한다. 획득은 `(user_id, ar_character_id)`
기준이라 이미 보유했으면 행을 만들지 않는데, 그때도 **응답은 뽑힌 캐릭터를 그대로** 준다.
"보유 → 다시 추첨" 이나 "보유 → 응답 null" 로 구현하기 쉬워서 후보 셋을 모두 보유한 상태를 만들어 본다.
걸음 수 달성 보상은 미션 보상이 아니므로 `acquired_mission_id` 가 **`NULL`** 인지도 함께 본다.

다섯째, **달성 여부의 판정 주체**다. `isGoalAchieved` 는 프론트가 판정해서 보내는 값이고
서버는 저장하지도, 걸음 수와 목표 걸음 수를 다시 비교해서 뒤집지도 않는다.
그래서 `stepsCount = 1` + `isGoalAchieved = true` 로도 캐릭터가 지급되는지 확인한다.

동시 요청은 실제로 두 요청을 겹쳐 보낼 수 없으므로,
**조회 직후 다른 요청이 행을 먼저 만든 상황**을 조회 함수 스텁으로 흉내 낸다.
(우리 쪽 조회 결과는 `None` 인데 DB 에는 행이 있는 상태 → INSERT 가 유니크 제약에 걸린다)

### 주요 검증 항목

#### 1. 신규 저장

- **200** 이고 응답은 `characterName` / `characterImageUrl` / `targetStep` 세 필드다.
- `targetStep` 은 걸음 수 기록이 아니라 `USER.target_step` 이다.
- `user_id` 는 토큰의 사용자, `steps_count` 는 요청값이다. (Body 로 사용자 id 를 받지 않는다)
- `saved_at` 은 요청의 `recordedAt` 그대로다. (자정으로 정규화하지 않는다)
- 걸음 수가 `0` 이어도 저장한다.

#### 2. 같은 시각 재요청

- 행을 추가하지 않고 **`steps_count` 만 갱신**한다. (행 1개 유지, `created_at` 유지)
- **기존 값보다 작아도** 요청값으로 덮어쓴다. (최댓값 선택·누적 합산을 하지 않는다)

#### 3. 키 범위 (`user_id` + `saved_at`)

- 측정 시각이 다르면 새 행이 생긴다.
- 다른 사용자의 같은 시각 기록은 건드리지 않고 사용자별로 행이 따로 생긴다.
- 토큰을 바꾸면 그 사용자의 기록으로 저장된다.

#### 4. 동시 요청 (유니크 제약)

- `(user_id, saved_at)` 유니크 제약이 DB 수준에서 중복 행을 막는다.
- 조회 직후 다른 요청이 먼저 행을 만든 상황에서도 **중복 행을 만들지 않고**
  기존 행을 요청값으로 갱신한다. (`created_at` 유지)

#### 5. 목표 달성 캐릭터 추첨과 획득

- `isGoalAchieved = true` 면 후보 캐릭터(1~3) **중 하나**의 이름·이미지 URL을 응답한다.
  여러 번 호출해도 후보 밖 캐릭터는 뽑히지 않는다.
- 획득 기록이 생기고 `acquired_mission_id` 는 **`NULL`** 이다.
- 이미 보유한 캐릭터가 뽑히면 **중복 행을 만들지 않지만** 응답에는 그 캐릭터를 그대로 준다.
- 보유 판단은 현재 사용자 기준이다. 다른 사용자의 획득 이력은 쓰지 않는다.
- `isGoalAchieved = false` 면 추첨도 획득도 없고 캐릭터 두 값이 `null` 이다.
- 달성 여부는 프론트 판정을 그대로 믿는다. (`stepsCount = 1` 이어도 지급한다)
- 후보 캐릭터가 하나도 없으면 **500** 이고 걸음 수도 저장되지 않는다. (전체 롤백)

#### 6. 400 `INVALID_REQUEST`

- 측정 시각·걸음 수·달성 여부 누락, 음수 걸음 수, 정수가 아닌 걸음 수,
  offset 이 붙은 `recordedAt`, 형식이 아닌 시각, 정의되지 않은 필드, 빈 body
- 모두 DB 에 걸음 수 행과 획득 기록이 남지 않는다.

#### 7. 401 `UNAUTHORIZED_USER`

- 인증 헤더가 없거나 토큰의 사용자가 없으면 401 이고 행이 남지 않는다.
- Swagger 문서 응답은 200/400/401/500 이다.

## GPS 및 방문 장소 저장 테스트 의도

요청 한 번이 **두 테이블에 쓰는** API 라, 저장 자체보다 "무엇을 언제 남기는가"가 검증 대상이다.
여기도 응답이 204라 확인은 전부 DB 행을 직접 읽어서 한다.

첫째, **좌표 축**이다. 요청은 `latitude` / `longitude` 인데 DB 는 `my` / `mx` 다.
둘을 바꿔 넣어도 저장은 성공하고, 제주 좌표(33/126)는 두 값이 모두 유효 범위라
**범위 검증으로도 걸리지 않는다.** 그래서 위도·경도를 서로 다른 값으로 보내
`my`/`mx` 에 각각 제대로 들어갔는지 본다.

둘째, **시각의 출처**다. `saved_at` 과 `visited_at` 은 모두 요청의 `recordedAt` 이다.
서버 시각(`now_kst()`)을 쓰면 테스트가 실행되는 순간에도 값이 그럴듯해서 티가 안 난다.
그래서 과거 시각을 보내고 두 테이블의 값이 **그 시각과 정확히 같은지** 확인한다.

셋째, **판정 결과의 개수**다. 반경이 겹치면 걸린 장소를 **모두** 남겨야 하는데,
가장 가까운 한 곳만 고르는 구현도 "방문 기록이 생긴다"는 확인만으로는 통과한다.
그래서 반경이 겹치는 장소 두 곳을 만들어 두 건이 다 생기는지 본다.

넷째, **중복 제거를 하지 않는다**는 점이다. 지금 단계는 진입/이탈을 추적하지 않으므로
반경 안에 머무는 동안 요청마다 방문 기록이 쌓이는 게 정상이다.
"같은 장소는 한 번만"으로 만들어 버리는 실수를 막으려고 두 번 호출 후 4건을 확인한다.

판정 규칙 자체(경계 포함, 반경 중첩, 반경별 차이)는 DB 없이
`test_visit_detector.py` 에서 따로 본다. 이 모듈은 좌표와 장소 목록만 받는 순수 함수라
나중에 판정 방식이 바뀌어도 이 테스트만 갈아끼우면 된다.

### 주요 검증 항목

#### 1. GPS 저장

- **204** 이고 응답 본문이 비어 있다.
- `longitude → mx`, `latitude → my` 로 저장한다.
- `saved_at` 은 서버 시각이 아니라 요청의 `recordedAt` 이다.
- `user_id` 는 토큰의 사용자다. (Body 로 사용자 id 를 받지 않는다)
- 걸음 수와 달리 **upsert 가 아니다.** 같은 좌표를 여러 번 보내면 기록이 그대로 쌓인다.

#### 2. 방문 장소 판정

- 반경 안이면 `VISITED_LOCATION` 을 함께 남기고, 밖이면 GPS 만 남긴다.
- 방문 시각은 GPS 와 **같은 `recordedAt`** 이다.
- 반경이 겹치면 걸린 장소를 **모두** 기록한다. (가장 가까운 한 곳만 고르지 않는다)
- 멀리 있는 장소는 잡히지 않고, 다른 장소로 이동하면 그 장소가 기록된다.
- 반경 안에 머물면 **요청마다** 방문 기록이 쌓인다. (중복 제거 없음)
- 방문 기록의 사용자도 토큰의 사용자다.
- 장소가 하나도 없어도 GPS 저장은 성공한다.

#### 3. 판정 규칙 (`visit_detector`)

- 반경 안이면 방문, 밖이면 아니다. 장소가 없으면 빈 목록이다.
- **경계(거리 == 반경)는 방문으로 본다.** 1m 만 좁아도 빠진다.
- 반경이 겹치면 모두 반환하고 입력 순서를 유지한다.
- 같은 지점이라도 반경이 다르면 결과가 갈린다.
- 남반구·서반구 좌표도 같은 규칙으로 판정한다.

#### 4. 트랜잭션

- 커밋이 실패하면 GPS 기록과 방문 기록이 **둘 다** 남지 않는다.

#### 5. 400 / 401

- 시각·위도·경도 누락, 좌표 범위 밖, 형식이 아닌 시각,
  **offset 이 붙은 시각**, 정의되지 않은 필드, 빈 body → **400 `INVALID_REQUEST`**
- 시각 없이 날짜만 보내면 그 날 자정으로 해석해 저장한다. (400 이 아니다)
- 인증 헤더가 없거나 토큰의 사용자가 없으면 **401 `UNAUTHORIZED_USER`**
- 모두 DB 에 아무것도 남지 않는다.

## 실행 방법

```bash
# 최초 1회
pip install -r requirements-dev.txt

# 전체 테스트
pytest

# 기타 도메인만
pytest app/others

# 특정 테스트만
pytest app/others/tests/test_save_step_count.py -k 갱신
pytest app/others/tests/test_save_step_count.py -k 유니크
pytest app/others/tests/test_save_gps.py -k 방문
pytest app/others/tests/test_visit_detector.py
```

DB는 SQLite 인메모리를 사용하므로 MySQL이 떠 있지 않아도 실행된다.
공통 픽스처(`client`, `db_session`)는 루트 `conftest.py`에 있고,
사용자 두 명은 `step_data` 픽스처에서 만든다.
걸음 수 기록은 테스트마다 조합이 달라서 `_add_step_count()` 헬퍼로 직접 만든다.
응답이 204라 검증은 대부분 `_step_counts()`로 DB 행을 직접 읽어서 한다.
GPS 테스트는 `gps_data` 픽스처로 사용자 2명과 장소 3곳(반경이 겹치는 2곳 + 멀리 있는 1곳)을 만들고,
`_gps_records()` / `_visits()` 로 두 테이블을 각각 확인한다.
`test_visit_detector.py` 는 DB 픽스처를 쓰지 않는다.
